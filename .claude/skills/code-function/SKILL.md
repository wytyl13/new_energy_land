# 函数编写规则

边界：只管函数与脚本组织。类的内部结构归 `code-class`，
分层归属归 `code-decoupling`。

## 1. 最少代码判据（写之前按序判断，停在最先成立的一档）

1. 推测出来的需求（"以后可能要"）→ 不写；
2. 项目内已有同职责函数 → 复用，不再写一份；
3. 标准库/已装依赖能做 → 直接用；
4. 一行可读表达式能表达 → 不包函数；
5. 以上都不成立 → 写最少量实现。

硬约束（简洁的代价上限）：

- 不为省代码牺牲性能与效率（该有的索引、向量化不省）；
- 校验、错误处理、类型注解、冻结约定照旧，一项不减；
- 封装须有 ≥2 个调用方或一段独立逻辑，否则内联；
- 改需求先删旧路径再写新路径，删代码优先于加代码。

## 2. 函数还是类（先全局，后局部）

判断顺序：**先从项目全局分析实体结构，再落到单个文件**。
全局结论优先于局部默认。

### 2.1 全局判断（优先做）

从项目整体看，满足以下情形时直接按类组织，
不受下面"默认函数"限制：

- 存在**多个同类实体**（如 8 个电源），结构一致：
  字段相同、操作步骤相同（如每实体固定两步）；
- 此时最优结构：**每实体一个类 + 一个模块文件**；
  公共字段与公共步骤放基类（或统一接口），各子类只写差异；
  禁止把同一组函数按实体复制多份、或用多组独立函数加
  实体编号参数区分。

### 2.2 局部判断（全局无多实体结构时）

**默认全部用函数，不确定时不封装。** 仅当满足以下条件之一，
才把一组函数封装为类：

- 一组函数反复传递同一批数据（同一组参数出现 3 处以上），
  传参冗长；
- 数据天然聚合成一个实体（一类设备、一张表的结构），
  用数据类装数据（见 `code-class`）；
- 需要跨多次调用保持状态，或有"初始化一次、多处使用"的
  生命周期。

### 2.3 单个脚本内部的组织

| 情形 | 组织方式 |
| :--- | :--- |
| 流程短且线性 | 模块级函数 + `main()` 入口 |
| 多个操作围绕同一批数据 | 数据装数据类，操作仍是函数 |
| 操作与状态强绑定、天然是一个实体 | 整体封装为类 |

## 3. docstring 格式（固定）

- 首行：一句话说清做什么。
- `Args:` 每个入参 `名字（类型）：中文含义`。
- `Returns:` 写 `类型：中文含义`；无返回值写 `Returns: None`。

```python
def weighted_sum(w: np.ndarray, X: np.ndarray) -> np.ndarray:
    """按权重对矩阵各行加权和求和。

    Args:
        w (np.ndarray): 权重向量 (N,)。
        X (np.ndarray): 数据矩阵 (N, T)。

    Returns:
        np.ndarray: 各时段加权和 (T,)。
    """
```

## 4. 签名规则

- 类型注解强制。
- 统一签名：同类函数签名保持一致，用不到的入参直接忽略，
  **不开特例、不加第二个变体**。
- 默认参数只用于向后兼容的新增项（见 `process-workflow` 影响面评估）。

## 5. 职责规则

- 一个函数做一件事；取数、计算、保存文件不混在一个函数里。
- 全项目同一职责只有一个出口函数（如：只有一处调底层库），
  其他地方复用，不各自实现。
