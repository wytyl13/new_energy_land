# 解释与回答规则

边界：只管"怎么对用户解释"，不管代码怎么写。
文字用词规范归 `style-wording`。

## 1. 名词规则

- 新名词第一次出现必须先给一句白话定义，再拿它推理。
- 没定义过的词不直接用。

## 2. 一次一问

- 只答用户当前问的那一个问题（但该问题要解释全面），
  不预支后续内容；用户按自己的顺序追问。

## 3. 短优先

- 一句话结论 + 表格/短列表；不用长段落、不堆叠多重类比。
- 被指"太复杂"时：砍篇幅重写，不在原结构上叠加补救性解释。

## 4. 分层讲解

- 复杂问题先给一句话版本，用户要哪层再展开哪层。
- 先判断用户对项目的理解程度，宏观或微观**二选一**，
  不同时展开。
- 微观讲解循序渐进：确认前一层理解后，再讲下一层；
  严谨列出所有细节。
- 简单问题不复杂化，复杂问题必须简单化。

## 5. 操作类问题的回答结构（五段，缺一不可）

用户问"怎么做 / 怎么备份 / 怎么恢复 / 某参数是啥"这类操作问题时，
按固定结构回答：

1. **直接结论**：先答问题本身（是/不是、用的什么方法），一句。
2. **指令**：可直接复制的完整命令。
3. **功能**：这条指令执行后发生什么。
4. **找回旧版**：做完想反悔时，怎么恢复到之前的状态（给指令）。
5. **逐符号解释**：指令里每个参数、每个 ID 的含义，
   以及**从哪条指令拿到它**（如提交号从 `git log --oneline` 拿）。

- 指令中出现的哈希、编号、路径，必须同时给出获取方式，
  不允许出现来路不明的值。
- 只答被问的维度，不铺开没被问的概念。
