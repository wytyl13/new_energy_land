# 改代码

## 1. 先定位

- 修 bug：先找根本原因，在回复里写出分析过程、推导、结论，三者都要有
- 加功能：先说清要动哪些已有代码、新代码放哪一层（分层见 `design-module-layering`）

## 2. 评估影响面

- 只处理用户当前提的问题，不跑题
- 要改被多个模块调用的代码时，先停下回答：谁在调用它；改了会不会破坏其他模块或导致测试失败
- 有兼容风险时，给不破坏现有调用方的方案：新增带默认值的参数，或只在当前模块局部处理

## 3. 分步修改

- 按 Step 1、Step 2… 列出思路，每步写验证方法
- 上一步验证通过（或用户确认）后再做下一步，不一次给出全部代码
- 改需求时先删旧路径再写新路径
