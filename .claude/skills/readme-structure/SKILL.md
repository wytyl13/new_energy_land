# README 编写规则

边界：只管"README 怎么写"。何时随代码同步归 `process-doc-sync`，
文字用词规范归 `style-wording`。规则通用，不绑定具体领域，
示例中的"实体/单元"按项目实际命名替换（如电源/机组/地市）。

## 1. 宏观：章节顺序固定

README 自上而下按以下顺序组织，先宏观后微观：

| # | 章节 | 内容 |
| :--- | :--- | :--- |
| 1 | 背景 | 一段话说清：项目做什么、输入是什么、输出是什么 |
| 2 | Quick Start | 环境安装、核心运行命令、服务启动（如有） |
| 3 | 架构 | 分层图 + 各层职责表 |
| 4 | 算法全流程 | 端到端数据流主线（核心章，见第 2 节） |
| 5 | 分实体明细 | 每个实体/单元：描述、约束、成本、输入数据、输出数据 |
| 6 | 汇总输出 | 输出文件表：文件名、内容、产出模块 |
| 7 | 接口 | 服务端点（如有）：传参、返回示例 |
| 8 | Reference | 编号引用映射表，只在文末 |

- 每章开头用一句 blockquote 概括本章说了什么。
- 缺哪章就空缺，不编造内容；服务项目才写接口章。

## 2. 核心：算法全流程章

把算法拆成流程步骤，**每一步必须写清三段**：

- **输入**：从哪来（数据文件 / 上一步输出 / 配置），引用到代码位置；
- **中间步骤**：做什么变换或计算，在哪个模块发生；
- **输出**：产出什么（数据结构 / 文件），交给下一步谁用。

写法：开头一句数据流总述（如"读数 → 计算 → 结果文件"），
再配一张主流程表：

```markdown
| 步骤 | 输入 | 中间处理 | 输出 | 模块 |
```

- 步骤顺序 = 实际执行顺序；每行的输入能追溯到上一行的输出
  或外部文件，中间不许出现来源不明的数据。
- 分支/可选步骤（如评估、出图）单列一行标注"可选"。

## 3. 微观：各章细节规则

### 3.1 背景与 Quick Start

- 背景只写三件事：做什么、输入、输出；不写背景铺垫和修饰词。
- 命令块必须可直接复制执行；环境名、执行命令、必要环境变量写全。

### 3.2 架构

- 分层图用 ASCII，依赖单向、自上而下，标注"按项目实际裁剪"。
- 各层职责表列集固定：模块 | 职责 | 编写规则；
  编写规则列引用对应规则文件，不在 README 里重复展开。

### 3.3 分实体明细

- 实体行统一两种列集：
  - 描述 | 约束 | 成本；
  - 输入数据 | 输出数据（含决策变量、成本项）。
- 输入输出条目逐项编号引用，不裸写。
- 实体较多的，先用一张分类总表（类型 → 实体列表），再逐实体展开。

### 3.4 汇总输出

- 每个文件一行：文件名 | 内容 | 产出模块。
- 结果比对基准件单独标注"列集冻结"。

### 3.5 接口

- 每个端点：传参、返回，均给最小可读示例；
- 示例 JSON 每个字段的注释必含两项：必填/可选（可选附默认值）、用途含义。
  传参与返回同等要求；同构端点（如风电/光伏）的差异字段也不例外，
  只写"可选，默认 X"不写用途即违规。

## 4. 引用规则

- 正文引用代码位置统一 `[n]` 编号，映射表集中在文末 Reference。
- 编号只增、不复用、不删；代码行号变了同步改映射表。
- 映射表按实体分组注释（如 `<!-- 某实体 xxx.py -->`），
  方便维护时定位。

## 5. 用词

- 遵守 `style-wording`：平实技术语言，不用禁用词
  （用"写文件"不用"落盘"，用"结果比对"不用"对拍"，
  用"固定不变的对外约定"不用"合同"）。
- 表格对齐、章节顺序、标点沿用文档原有格式，不顺手美化。
