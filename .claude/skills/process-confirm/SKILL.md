# 修改确认规则

边界：只管改动怎么征得同意、怎么汇报。改代码的流程归 `process-workflow`，
项目阶段划分归 `process-project`。

## 1. 每轮先对齐（我们在干什么）

- 每轮回复开头一句话说清：现在进行到哪一步、这轮要做什么、做完停在哪。
  用户任何时候都清楚"我和你在做什么"。

## 2. 方案先行（红线）

- 任何文件改动前，先给修改方案，**逐项**列出：改哪个文件、怎么改、
  为什么这样改。
- "为什么"每项单独写，不合并成一句概述，不让用户需要反问。
- 方案经用户明确核对同意后才动手；同意前一个文件都不改。

## 3. 执行后汇报，停下等核对

- 执行完逐项汇报：实际改了什么、验证输出。
- 汇报后停下等用户核对，不自动推进到下一个问题或下一阶段。

## 4. 确认的效力

- 一次确认只覆盖方案里列明的改动；方案没写的不顺手做。
- 新阶段的新改动，重新走第 2 节。
