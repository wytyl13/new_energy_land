# 设计文档规则

边界：只管 DESIGN.md 的结构与维护。README 归 `readme-structure`，
建项目的流程归 `project-bootstrap`，同步时机细则归 `process-doc-sync`。

## 1. 何时建

- 任何新项目或重构开工前，先在项目根目录建 `DESIGN.md`；
  它是该项目的唯一设计与规划文件，从开工维护到收口。

## 2. 章节固定（缺章空缺，不编造）

| # | 章节 | 装什么 | 变更频率 |
|---|---|---|---|
| 1 | 定位 | 项目做什么、输入、输出（两三句） | 定稿后基本不动 |
| 2 | 需求 | 已确认的需求，分组列出 | 定稿后冻结，改要留痕 |
| 3 | 数据设计 | 核心数据/对象的格式与约束（文件格式、数据结构、口径） | 定稿后冻结 |
| 4 | 结构设计 | 目录布局、模块划分、职责、依赖方向 | 定稿后冻结 |
| 5 | 接口设计 | 对外接口：CLI / MCP / API / UI | 细化后冻结 |
| 6 | 实施规划与进度 | 宏观步骤表（步骤/状态/验证结果）+ 当前进行到哪 | 唯一高频更新区 |
| 7 | 决策记录 | 每个拍板：日期/问题/选择/理由 | 只增 |

- 每章开头一句 blockquote 概括本章内容。
- 状态一律用文字：未开始/进行中/已完成/搁置。

## 3. 同步与确认（本文件是确认界面）

- 每完成一步设计或执行，**先同步进 DESIGN.md，再请用户确认**；
  用户核对的对象是文档，不是聊天记录。
- 阶段状态一变就更新 §6；要改 §2–§5 冻结区，先在 §7 留痕再改正文。

## 4. 与其它文件的关系

- CLAUDE.md 的"当前进度"两三行从 §6 摘要，不另写一份。
- README 只写稳定的项目说明（是什么/怎么跑），不装进度。
- 项目演变历史 = git 提交 + DESIGN.md §7，不另建文件。

## 5. 重构类项目的表述结构

边界：只管重构/移植类项目在 DESIGN.md 里怎么表述；
表述时机（动代码前先写、重构收口后并列补写）归 `algo-porting`。

- 顶层以待构建项目为标题；其下按子项目分标题，一个项目也单独成节。
  子项目章节就是文档主体，**取代**通用结构里的"定位 / 数据设计 / 结构设计"
  三章（基本情况并入定位、输入数据并入数据设计、数据流转步骤并入结构设计）；
  需求 / 接口 / 进度 / 决策照常保留。
- 每个子项目依次写四段，写完循环下一个：
  1. **基本情况**：这个项目是干啥的，一两句；
  2. **输入数据**：数据多就用表（数据 / 维度 / 原始数据路径）；
  3. **数据流转步骤**：每步给算法与处理、处理后维度、`文件:函数`
     （精确到函数）；末尾迭代循环 for 结构图（循环体内 / 外各做什么）；
  4. **输出**：同输入格式（数据 / 维度 / 路径）。
- 重构设计同此结构，另加一段**重构步骤细节**（动哪些文件、怎么动、
  回归判据）。
- 确认链：原始表述经用户确认 → 出重构设计 → 用户确认 →
  按重构思路执行。
